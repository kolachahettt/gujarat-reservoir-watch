# Regenerating the data

Nothing under `data/raw/` or `data/interim/` is in git. All of it is either re-fetchable
from the source or derivable from what is. This file says how, and what you should get.

The small derived CSV and JSON in `data/processed/` **are** committed, because they are the
audit trail the README and `PROJECT_BRIEF.md` cite. The rule is size and reproducibility,
not "derived" as such.

## Regenerating the reservoir dataset

Three steps, in order. Only the first touches the network.

### 1. Download the daily reports

```bash
python scripts/backfill.py --download-only --months 6-10 --delay 1.0
```

**This takes hours, and that is the server's doing, not the script's.** Each PDF is
generated on demand and takes about 33 seconds. 716 dates at ~34 s is roughly 6.5 hours for
a cold cache. The download is deliberately serial and polite: one request at a time, a fixed
delay between *network* calls, cache hits never sleeping, an identified User-Agent, four
attempts per date with jittered exponential backoff, and a five-minute cooldown after six
consecutive failures.

It is resumable. **Re-run the same command** to pick up anything that failed — cached dates
cost a `stat` to skip. Expect to need more than one pass: the first full run lost 133 dates
to transport failures in runs of 24–50 consecutive days, and a second pass recovered 132 of
them.

Two dates will never arrive, and that is correct: **`2025-09-26` and `2026-09-12` return
HTTP 200 with `Content-Type: application/pdf` and `Content-Length: 0`.** That is how this
server says "no report for that date" — it does not use 404. They are recorded as
`empty_upstream`, never retried again, and named in the interface. Expect **714 of 716**.

### 2. Parse, build, check, report

```bash
python scripts/run_pipeline.py --date 2026-09-11 --skip-pin
```

Parses every cached PDF across worker processes (~13–17 s per 23-page file, so budget
35–40 minutes for a cold parse at 7 workers), rebuilds DuckDB, runs the capacity gate, and
prints both deviation tables and the scheme-drift check.

**The pipeline refuses to run while any requested date is missing.** That is deliberate: a
deviation table built on a quarter of a season looks exactly like one built on all of it, so
incomplete coverage is blocked rather than footnoted.

**It also halts on an unacknowledged mid-season capacity change** (exit 2, and it writes
`data/processed/GATE_TRIPPED.txt`). Three are known and dispositioned — Shetrunji 2024, Jhuj
2025, Kelia 2025. A fourth is news and needs a human decision, because excluding a
scheme-season from the baseline is not a call the code should make on its own.

### 3. Build the site data

```bash
python scripts/build_view_data.py
```

Writes `web/data/reservoir_view.json` (~220 KB). All view computation happens here; the page
contains no analysis.

## Verifying you got the same data

The ledger at `data/interim/backfill_ledger.csv` records the byte count and **SHA-256 of
every downloaded file**. That matters more than usual here: TLS certificate verification is
deliberately disabled for `wrd-dam.gujarat.gov.in`, which does not validate in this
environment, so the content hash is the integrity check — the transport is not one.

The 11 September 2026 report should be **276,237 bytes**, SHA-256
`10F4783D812B83530D6B108AC131E4B03FDA075B48778183369BF4B60B2C4C28`.

A clean run should give:

| | Expected |
|---|---|
| Daily reports loaded | 732 (714 in-season + 18 off-season probes) |
| Storage rows | 150,792 |
| Schemes on every date | exactly 206 |
| Ledger | 542 `ok`, 190 `ok_with_warnings`, 2 `empty_upstream`, **0 failures** |
| Scheme drift | 0 added, 0 dropped, 1 renamed |
| Capacity classes | 1021 `clean`, 6 `edge_exception`, 3 `mid_season` |
| State position, 2026-09-11 | 65.29% of design capacity |

The 18 off-season dates are not part of the Jun–Oct range. They were fetched by
`pin_changeover.py` to date the capacity changeovers and are kept because they are real
reports; they are **excluded from season grouping** (see `check_capacity.py`, which explains
why relabelling them by water year does not work).

## Coordinates and the map

The WRD report publishes district and taluka for every dam and **never a coordinate**, so
the positions come from a second source: CWC's National Register of Large Dams 2019, which
gives a latitude and longitude for all 632 large dams in Gujarat.

```
python scripts/build_dam_coords.py     # fetches NRLD if absent, writes both CSVs
python scripts/build_view_data.py      # picks them up; the map switches on
```

| Path | Committed | What it is |
|---|---|---|
| `data/raw/nrld/nrld-2019.pdf` | no | 6,195,437 bytes, re-fetched by the script; SHA-256 in the sidecar `.provenance.json` |
| `data/reference/dam_coordinates.csv` | **yes** | 179 placed dams, each with the evidence that placed it |
| `data/reference/dam_coordinates_excluded.csv` | **yes** | the 27 not placed, with a reason each |

**179 of 206 dams are placed — 98.5% of design capacity**, because the unplaced are nearly
all small schemes. `mapSVG()` draws state and district geometry as strokes only, never
fills, so no colour on the map stands for a district, and the page states its own coverage.

**Nothing is placed on a name resemblance.** Every coordinate is corroborated by capacity
(WRD's design MCM against NRLD's gross m³) or by geography (the point falling inside the
district WRD assigns it), and the CSV records which. See `PROJECT_BRIEF.md` §24 for the
thresholds and how each was set.

### Two corrections to what this file used to say

It claimed the NRLD coordinate pages have "no ruled lines". **They are ruled** — the rules
are `rect` objects, not `line` objects, so `page.lines` is empty while `page.rects` holds
1,857 of them. That single wrong reading is what made the extraction look impossible; the
grid gives exact column boundaries once you look for it in the right place.

It also lumped the 2019 and 2023 editions together. They are completely different documents:
2019 is digitally generated and yields 632 of 632 coordinates, while **2023 is a scan with
an OCR layer** and is unusable — 16 of its coordinates land outside Gujarat, mostly reading
`89°` where the value must be `69°`, and it disagrees with 2019 by more than 2 km on 109 of
the dams they share. Do not reach for 2023; §24.4 has the measurements.

## Command area, and the 40 schemes that have one

The daily report never says who depends on a reservoir. Command area comes from
the **Gujarat NWRWS Data Bank**, one page per dam, which is the only source
found that publishes it per scheme — NRLD has no such column (all 20 were
checked), the live WRD host serves only daily PDFs, India-WRIS refuses
connections and data.gov.in returns 403, and the department's own
irrigation-potential documents are circle- and district-level.

```bash
python scripts/build_command_area.py --fetch
```

That fetches `showpage.aspx?contentid=1467` and the 136 per-dam pages into
`data/raw/nwrws/` (gitignored, ~13 MB, about 30 minutes at one request per
second), then writes:

* `data/reference/scheme_command_area.csv` — the 40 verified schemes, with GCA,
  CCA, maximum ever irrigated and its year, scheme class, and the match tier
* `data/reference/scheme_command_area_excluded.csv` — all 254 rejections, each
  with the reason

**The source is unreliable row by row, and the script says so per row.** Of the
102 pages that parse, 9 carry a different dam's row (`Bhogavo-2`'s page holds
Bhogavo-1's), 6 contradict their own second table (Shetrunji by 23x, 57,060
against 2,514 ha), and 2 pairs share one row. Each page prints GCA/CCA twice,
which is what makes the errors detectable. 40 of 206 survive; the page states
that coverage. See PROJECT_BRIEF.md section 26.

One reading trap the file encodes rather than flattens: **`max_irrigated_ha`
empty means NOT RECORDED**, because the source leaves the year blank for those
nine schemes. It does not mean zero hectares, and six of the nine are Kutch
schemes.

The figures are old. Maximum-irrigation years run 1979-80 to 2007-08 and the
department's statewide season-wise table ends 2007-08, so the command areas
predate the SAUNI transfers into Saurashtra.

## The archived basis-risk project

`archive/` holds the predecessor project, finished and kept separate. Its source data
(SHRUG village-level `.dta`, admin boundary `.gpkg`) is ~2.4 GB and excluded; SHRUG requires
accepting its own terms at <https://www.devdatalab.org/shrug>, so it cannot be redistributed
here in any case. `archive/ARCHIVE_basis_risk_BRIEF.md` records what was downloaded and
which modules were selected.

Its PMTiles are excluded for size and are rebuilt with `archive/scripts/build_tiles.py`.
**The archived viewer will not render a map when deployed to a static host** — the tiles are
not in the repository and are too large for one.
